docintel_kit

One Python toolkit for document parsing, OCR, layout analysis, table extraction, structured field extraction, LLM tasks, and RAG — built around a single shared data model, so a table from a scanned PDF and a table from an Excel sheet look identical to everything downstream.

View on GitHub → Capabilities Quick start Test results

Why

Most document-AI stacks bolt together five or six single-purpose libraries with incompatible data models. docintel_kit gives you one Table, one Document, one ParseResult — produced consistently whether the source was a PDF, a scanned image, an Excel sheet, or a PowerPoint deck — so an LLM prompt, a RAG index, or a CSV export never needs to know where the data came from. Every capability sits behind a swappable Base*Backend interface, so you can register your own OCR engine, extraction model, or vector store without touching call sites.

Quick start

from docintel_kit import parse_document, run_ocr, extract_tables_from_document, extract_fields

# Parse a text-layer PDF, DOCX, PPTX, or HTML file
result = parse_document("invoice.pdf")
print(result.get_page_text(0))

# OCR a scanned document or photo
ocr_result = run_ocr("scanned_invoice.pdf")
print(ocr_result.full_text)

# Extract tables (PDF ruled tables via camelot, with OCR fallback for scans)
tables = extract_tables_from_document("invoice.pdf")
df = tables[0].to_dataframe()

# Ask natural-language questions about a form/invoice's fields
result = extract_fields("invoice.pdf", schema={
    "invoice_number": {"type": "string"},
    "total_amount": {"type": "amount", "question": "What is the total amount due?"},
})
print(result.get_field("invoice_number").value)

Design notes

Structured extraction uses a QA model, not a generic pretrained checkpoint

An earlier version used microsoft/layoutlmv3-base directly, which turned out to have no fine-tuned classification head — its output labels were generic placeholders, making it structurally incapable of answering arbitrary field questions regardless of input quality. extract_fields() now uses impira/layoutlm-document-qa, a checkpoint fine-tuned for document question-answering, and converts each scalar schema field into a natural-language question — which is what makes zero-shot extraction against arbitrary schemas actually work.

Every backend is swappable

register_parser_backend, register_ocr_backend, register_layout_backend, register_extraction_backend, register_llm_client, and register_vector_store let you drop in your own implementation — a different OCR engine, a fine-tuned extraction model, a persistent vector store like Qdrant or PGVector — without touching call sites.

One shared Table model

Tables extracted from a PDF via camelot, tables recovered from a scanned image via layout+OCR, and tables loaded from an Excel sheet all produce the same Table object, with the same to_dataframe(), to_csv(), and to_json() export methods.

docintel_kit is local-first: no SaaS calls by default. LLM-backed functions (summarization, classification, table QA) are optional and only call out to a network engine when explicitly requested.
